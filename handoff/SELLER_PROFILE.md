## 0. CREDITS — PO STANDING ORDER (2026-08-11, verbatim: "STOP, NEVER USE credits")
- The AI/pipeline assistant NEVER triggers any Jungle Scout credit-consuming action: no Intelligence enrich (`forceRefresh:true` is always billable), no keyword re-harvest, no research refresh, no bulk sweeps. Anything needing credits is proposed with an estimated spend and the PO triggers it personally.
- Before suggesting a regen, CHECK the ASIN's research freshness (`analyzed_at` vs TTL) so the suggestion itself cannot cost credits.
- **⚠️ CORRECTED 2026-08-13 — the kill switch is a DATABASE ROW, not the env var.** This line previously said `JUNGLE_SCOUT_ENABLED=off` in Coolify was the hard guarantee. That is WRONG. Verified at `src/lib/sync/jungleScoutClient.ts:44-71`: the client reads `app_settings` FIRST and, when `jungle_scout_api_key` + `jungle_scout_key_name` are present and `jungle_scout_enabled === 'true'`, returns enabled credentials at `:60-63` — **never reaching** the env check at `:69-71`. The env var is only a fallback for when those DB rows are absent. **The real kill is `UPDATE app_settings SET value='false' WHERE key='jungle_scout_enabled'`**, and a 30-second in-memory credential cache means it is not instantaneous.
- **⚠️ A SUCCESSFUL VISION SCAN ARMS A BILLABLE HARVEST ON THE NEXT REGEN.** Verified at `ai-recommendations/route.ts:557-566`: a new `product_identity` row makes `visionSig` non-empty → the reference fingerprint changes → `signalChanged` → `forceRefresh: true`, which bypasses both the 24-hour research cache and the 14-day shared seed pool. The spend lands on the FOLLOWING regen — fired by an ordinary Regenerate, including a title-only section regen. So "scan the listings that have no vision record" is a credit-spending action, not a free repair.

## 0b. HOW WORK IS DONE — PO STANDING ORDER (2026-08-12, verbatim: "NEVER patch, Always foundational via /karpathy-dev-principles")
- **Architecture before code.** When the right shape is unclear, research and propose first; deliver the design and the evidence, not a diff.
- **The repeat-fix circuit breaker fires on the SECOND fix in an area, not the third.** A recurrence means the first fix treated a symptom.
- **Fix the decision, not the output.** A deterministic net removes ONE instance of a defect; the component that CHOOSES the output is what determines whether the defect is produced at all. If the decider cannot measure the property being policed, that is the fix.
- **Adding an Nth entry to a list/regex/net is the disease, not the cure** — prefer deleting or unifying. Say plainly when something is a stopgap.
- Case study that earned this rule: five consecutive rejected titles (2026-08-11/12). Each fix closed the exact failing string; each regen produced a new variant through a different seam. Root cause was never the string — the scorer that picks the shipped title scored the PO's gold and a keyword-stuffed twin identically (100/100 both).

## 1. BRAND IDENTITY
- The brand is **THE CEO** (CEO® on packing slips). Every title **starts** with it — position 0, no exceptions (judge docks −20).
- The brand appears in the **title and brand attribute only**: never in description body prose (stripped, even inside quotes), never in backend keywords (the attribute already indexes it — the byte buys nothing).
- Garment-brand casing is authoritative from the spec table ("Comfort Colors", never "comfort colors").

## 2. GARMENT BLANKS & PRODUCT FACTS
- **Comfort Colors 1717** (confirmed): Relaxed fit, Short Sleeve, Crew Neck, midweight 6.1 oz garment-dyed, 100% Ring-Spun Cotton, Low Stretch, Runs Slightly Small. **The name IS a selling point** — it belongs in titles next to the money keyword.
- **Gildan 64000 Softstyle** (confirmed 2026-07-31): Classic fit, Short Sleeve, Crew Neck, lightweight 4.5 oz ring-spun. Material stated **without** a percentage (heathers are blends). **The name is NOT a selling point** — its facts feed copy, the word "Gildan" never appears in any customer-facing field. SKUs carry the style number (640002XL-…) as identification.
- **Spec beats search**: fit/weight/sleeve/neck/material come ONLY from the confirmed spec table, never inferred from keyword demand ("oversized" search volume does not make a relaxed tee oversized).
- **Weight truth**: pin the real fabric when the blank is known; claim NO weight when it isn't.
- **Production method**: garments are **printed**, never "screen-printed"/"silk-screened" (auto-rewritten to "printed").
- **Unisex truth**: the blanks are unisex — "women's fit"/"men's fit" fabricates a gender the garment doesn't have. Audience targeting ("for Women") is fine; fit-gendering is not.
- A new blank earns copy mentions only by being confirmed and added to the spec table (a PO confirmation like "Gildan 6400 - YES" is the trigger).
- **Mixed-blank families (PO decision 2026-08-04): family-level resolution STANDS.** The only mix we offer is Gildan 64000 + Bella+Canvas 3001, and they are near-identical (lightweight ring-spun cotton, short sleeve, crew neck); per-child blank resolution was considered and DECLINED as not worth the programming. First matching row over the family hay (Gildan, by id order) grounds the whole family. Revisit only if a genuinely different blank ever gets mixed into one family.
- **Gildan 64000 stretch/fit-to-size CONFIRMED 2026-08-04** (closes the §12 open): Low Stretch, True to Size — sourced from the official Gildan G64000 page ("Modern classic fit", 100% ring-spun cotton, no elastane) and applied to blank_specs by the PO. Rows also carry `source_url` provenance now.
- **The spec table lives in the DATABASE** (2026-08-04, migration 053): `blank_specs` in Supabase is the authoritative catalog — adding/correcting a blank is **one SQL INSERT/UPDATE, no deploy**; affected listings heal on their next regen (reader caches 5 min). The two rows above are seeded byte-identically; the same rows exist in code (`src/lib/fba/blankSpecs.ts`) only as a fail-open floor if the DB is unreachable. `brand_in_copy=false` encodes the Gildan rule; `match_pattern` is a case-insensitive regex over title/attributes/productType/SKUs (`\b64000` deliberately unclosed so "640002XL" matches). A fact-starved short ship now names its cure: SHIP_CENSUS title/description floor lines carry `factsGap:"blank.unknown"` when an apparel run matched no blank.

## 3. TITLES

- **⭐⭐⭐ THE GOVERNING RULE (PO ruling 2026-08-12) — TWO TESTS, BOTH SEMANTIC, BOTH UNIVERSAL.** Asked what makes their Espana gold right and the rejected World Cup titles wrong, the PO selected exactly two of four offered rules — and pointedly did NOT select the other two. This is now the top of §3 and it governs every rule below it.
  1. **EVERY CHARACTER MUST BUY A SEARCH TERM.** `THE CEO Espana Championship Tee Shirt 2026 Spain Jersey Football Soccer Cup` spends all 75 characters on words a shopper types. The rejected `THE CEO 2026 World Soccer Cup Tee for Men and Women Fans | Short Sleeve` spends **23 characters on "for Men and Women Fans"** and **14 on "| Short Sleeve"** — nobody searches either. A character that does not buy a search term is wasted.
  2. **THE IDENTITY MUST NAME A SPECIFIC SUBJECT, NOT ITS CATEGORY.** "Espana"/"Spain" is a concrete nameable thing the design is ABOUT. "World Soccer Cup" alone is the *category* — there is no design in it.
  - **WHAT THE PO DECLINED, and why it matters more than what they picked.** They did **not** pick "zero audience words, zero spec words" and did **not** pick "synonym breadth". So **audience and spec vocabulary are NOT banned** — they are banned only when *nobody searches them*. This RESOLVES the standing contradiction with gold #3 (`Puff Embroidery Cotton Twill Snapback Hat for Men`): puff embroidery, cotton twill, snapback hat, hat for men are all real searched phrases, so that gold is fully compliant. It also retires the framing of §3's "waste vocabulary" as a *list*: `Unisex`/`Classic Fit`/`Crew Neck`/`Short Sleeve` fail because they are unsearched **on a graphic tee**, not because they appear on a ban list. A list enumerates instances; this rule quantifies over every span.
  - **CONSEQUENCE — THIS IS AN LLM TEST, NOT A CODE TEST.** "Would a shopper type this?" and "is this the subject or the category?" have no external oracle in any table we hold. This is the measured basis for moving title SELECTION to a corpus-anchored referee (handoff/TITLE_ARCHITECTURE.md). It is also the first rule that **separates the anagram pair** — `…Cup Tee Shirt | USA Mexico Canada Football Tee` (identity = one subject + garment) beats `…Cup USA Mexico Canada Tee | Football Tee Shirt` (identity = category + a bolted-on country list) despite the two having an IDENTICAL word multiset and identical length. No length rule, vocabulary list or regex can decide that pair; rule 2 does.
- **⭐⭐⭐ TITLE WORDS DESCRIBE THE DESIGN — THEY DO NOT CHASE A DIFFERENT PRODUCT'S SEARCHES (PO ruling 2026-08-13).** Asked whether "USA Mexico Canada" in their World Cup gold was aimed at people searching those countries or was simply describing the design, the PO answered: **"No — it just describes the design."** The design is ABOUT the host countries, so the words belong in the title; but the system must NOT pursue `usa jersey` / `mexico soccer jersey` traffic, because a shopper who wants a real jersey will not buy a graphic tee.
  - **CONSEQUENCE 1 — the theme rater was RIGHT and my reading of it was wrong.** It scores `usa jersey` 0 and `futbol` 0 while scoring generic tees 2. Measured 2026-08-13 and initially recorded in TITLE_ARCHITECTURE §10 as "inverted". Under this ruling the JERSEY half of that verdict is correct: it is a different garment. (`futbol` at 0 is still unexplained and stays open.)
  - **CONSEQUENCE 2 — 2026-08-13's grounding carve-out produced the right words from the WRONG SOURCE.** Exempting vetted targets from the design-vocabulary test recovered `usa jersey`, and the council then wrote `| Futbol USA Mexico Canada` — the correct words, sourced from a keyword the seller does not want chased. A right output for a wrong reason is not a fix; it is a coincidence that will not generalise to the next design.
  - **THE CORRECT SHAPE.** The host countries must reach the title as DESIGN VOCABULARY (the design's own subject), not as keyword targets. Once "usa"/"mexico"/"canada" are grounded design words, `usa jersey` is STILL correctly dropped — "jersey" remains ungrounded — and the country words remain available. That is the ruling and the mechanism agreeing rather than fighting.
  - **PRODUCT-TYPE MISMATCH IS CODE'S JOB.** "is a jersey the same product as a tee" is decidable against the listing's own product type — an external fact, no judgement required. It belongs in a strike-only predicate, not in the referee's rubric.

- **⭐⭐⭐ THE LEARNING LOOP IS AUTHORIZED (PO ruling 2026-08-12: "Yes — use them automatically").** Every PO title rewrite becomes, with no action from the PO, BOTH a teaching example for the producer AND a permanent regression fixture the system may never fail again. The data already exists: `lock-title/route.ts` writes `before_value` (what we generated) and `after_value` (what the PO typed) to `listing_change_log` on every lock, and nothing has ever read it. Build `loadPoRejectPairs` over it (task #168) and retire `SEED_REJECT_PAIRS` — today's entire negative corpus is FOUR hand-typed pairs from ONE product, all sharing the same `after` string, i.e. diversity ≈ 1.
  - **The positive half already works this way**: `loadPoGoldTitles` reads the newest manual `title_source` rows and re-measures at runtime, so a PO lock becomes training data with no commit and no deploy.
  - ⚠ **THE RISK THIS CREATES, AND WHY IT IS ACCEPTABLE.** Nothing gates corpus entry, so any lock moves the DERIVED STATISTICS for every listing. This is not hypothetical — on 2026-08-12 a one-word revision to a single gold moved the council's stated identity ceiling from 10 to 7 and started docking a different gold. The mitigation is NOT to gate the corpus (that would re-introduce a human bottleneck the PO just removed): it is that **no statistic derived from the corpus may be stated to the producer as a law**. The architecture deletes the ceiling for exactly this reason. Golds are EXAMPLES; the referee reads them as evidence, not as arithmetic.
  - **A lock is not always an endorsement.** A PO may lock a title to stop a bad regen, to defuse a trademark risk, or in a hurry. Pairs are therefore weighted as *corrections* (this was wrong, that was right) rather than as gold exemplars, and every new pair enters the frozen probe suite as a REQUIRED-TO-FAIL case — which is the half that can never be gamed.

The new floor is a *ship gate*: short → refuse + surface. A gate that only refuses cannot author a defect; a gate that pads is exactly the failure class being removed. Consistent with the architecture's governing asymmetry: **code may FILTER, never ADD**.
  - **It must be LOUD, never silent.** This repo's signature incident class is a silent degrade that reads as success ([[retry-guard-armed-by-completion]], [[ai-quota-outage-looks-like-success]]). A refusal is a visible queue entry with a stated reason, never a no-op that looks like "no changes needed".
  - **Fire-rate is UNKNOWN and must be measured before it ships.** The traced door chain on B0GVV3XL4T was landing 33–54 chars; if that is typical this gate holds back many listings. The shadow phase (P3) logs the refusal rate and the PO sees the number BEFORE any behaviour change reaches a listing.
  - **A refusal is a research signal, not a title verdict.** Running out of search terms means the keyword pool is thin — see the `jungleScoutClient.ts:235` volume-DESC top-100 harvest defect ([[autoseed-picks-blank-brand-not-design.md]], task #144), which structurally prevents a niche design from harvesting its own keywords.
  - **Repetition buys nothing.** A second or third printing of an already-present term ("Later Gator Later Gator Later Gator", or Tshirt/Shirts/Tees/Shirt folding to one token) adds characters that buy no NEW search term, so it fails rule 1 without needing a separate stutter rule.

The PO's own guard is the gate: strip **only** when the removal frees space for a money keyword **or** the title still lands 70-75 after the facts pad; otherwise refuse, byte-identical. The facts pad is barred from re-adding the same vocabulary (one predicate, both ends), or a Gildan family would oscillate inside a single pass.
- **Noun ×2 is protected from the dedupe (2026-08-09)**: `collapseRepeatedWords` deduped significant words globally and was therefore deleting the second garment noun from gold #1 (72→66) and gold #3 (72→68) — the golds spend the noun once per side of the pipe. Garment-family words are now deduped PER ` | ` SEGMENT (max two); the #148 defect (a repeat inside ONE segment, "Tshirt, Tshirt") is unchanged.
- Title carries **1–2 keywords max**; no variant attributes (size/color); seasonal terms only when the design IS the occasion.
- Title-Case; existing uppercase (THE CEO, TShirt) preserved.
- **A PO-locked title is the spec** — never regenerated, survives every audit; risky (trademark) locked titles get a warning banner, never a hard block.

## 4. AUDIENCE & GENDER
- Lean set (male/female/lean_male/lean_female) → the title MUST carry the matching tail ("for Women" / "Women's" / "Ladies"). "for Men and Women" is **never** correct on a leaned listing.
- Universal design → audience tail is OPTIONAL; never force gender; a product keyword outranks a generic audience phrase in the 75-char budget.
- **Closed relational lexicons** (PO verbatim): FEMALE carriers = {wife, girlfriend}; MALE = {husband, boyfriend}. Bare pronouns are deliberately NOT carriers ("He's Golfing" is a women's shirt).
- **Hard lean** drops opposite-gender keywords everywhere (backend included); **soft lean** keeps both (cross-gender gift traffic is real).
- **Widow format**: "{Hobby} Widow/Wife" designs — the wearer is the SPOUSE, not the enthusiast. Never "for golf-loving women"; correct: "for the golf widow whose husband is always at the course". These spouse compounds ("golf widow shirt") are the money niche and get seeded deliberately.
- A gift design naming the recipient ("Best Husband Ever" on a ladies cut) blocks the opposite tail.
- A gender word appears at most ONCE in a title.
- **"for Men and Women" is a CHARACTER WASTE, not a feature (PO ruling 2026-08-09, on their own locked `THE CEO World Soccer Cup Soccer T-Shirt, Women'S T-Shirts for Men and Women` — verbatim: "is TERRIBLE and Wasting MEN, WOMEN")**: the inclusive tail eats ~20 of 75 chars that a money keyword should own. NEVER pair it with a gendered noun ("Women's … for Men and Women" is self-contradicting AND redundant). Universal design → prefer the top market-opportunity keyword in that space; use the audience tail only when nothing better fits. Also: casing artifacts like "Women'S" are defects — Title-Case must not capitalize the letter after an apostrophe.

## 5. KEYWORD PLACEMENT & BACKEND
- **Doctrine: backend is the overflow home.** Title = 1–2 money keywords; bullets = clean shopper prose (keywords only when natural, NEVER forced — bullets carry no coverage duty); description = facts + story; **backend = everything else** (synonyms, occasions, long-tail, misspellings). Coverage anywhere counts everywhere.
- Never duplicate a keyword in title AND backend (Amazon indexes a token once).
- **Backend bands**: 250-byte cap, fill to **240–250** ("why aren't we using the full 250?"), 220 strict floor, <190 = garbage. Per-color shade tails ~17 bytes on colored families (shared core 233). CRITICAL money keywords claim bytes first and are exempt from title-echo dedup.
- Banned backend filler: apparel/clothing/clothes/outfit/wear/fashion/trendy/stylish ("a promotional string, not keywords").
- **"Oversized" nuance**: never in visible copy (blank is Relaxed) — but allowed in backend (invisible indexing of real 636K/mo demand is not a claim).
- **Colors**: shared title/bullets carry NO color word; colors rank per-child via each child's own backend tail.
- **Seasonal**: strip only OFF-season terms — a Valentine design KEEPS "valentine" everywhere (its theme IS the holiday).
- **30 ranking-target seats**, one per search intent (no spelling-variant waste); theme-fit rated against a persisted PO-editable theme card; a thin niche design's own keywords are harvested and seat-reserved even at low volume.
- The 158→240 byte gap on thin designs is a **pool problem** — never "solved" by padding junk.
- **A DESIGN'S OWN SUBJECT TERMS ARE BAND 3 / CORE BY DEFINITION; BAND 2 IS RESERVED FOR GENERIC CATEGORY HEADS (PO ruling 2026-08-09, "Correct")**. Diagnosed live on B0GVV3XL4T: the 3-rater panel put `soccer shirt` and `futbol` in band 2 — the SAME band as `oversized tshirts for women`. Because `THEME_BAND_WEIGHT` multiplies every band-2 row by the same 0.85, the theme term **cancels out** between them and raw volume breaks the tie, so a 442K/mo generic apparel head outranked the design's own subject and only 2 of 86 rows reached band 3, leaving **14 CORE seats nearly empty**. The band DEFINITIONS were already correct (`3 CORE · 2 CATEGORY-UNIVERSAL · 1 GENERIC · 0 OFF`) — what was missing is that band 2's "true regardless of print" was never stated as an EXCLUSION, so the two breadth-defending personas could absorb design-subject phrases into 2 without contradicting anything they'd been told, and with the LOWER median two such votes decide. **THE RULE, now shared verbatim by all three raters (`PRINT_TEST`, src/lib/keyword-engine/themeRater.ts): "would this phrase still be true of this garment if a COMPLETELY DIFFERENT design were printed on it?" YES → band 2 (it describes the blank). NO, only true because of the print → band 3 if it is THIS design's subject, band 0 if it names a DIFFERENT theme.** Breadth is never a reason to demote a design-subject phrase, and a loose/informal phrasing of the subject is still band 3. Volume vocabulary stays OUT of the rater prompts entirely (volume enters once, deterministically, in the selector) — a guard test enforces this. Flag `THEME_PRINT_TEST`, **default ON** (it implements a ruling; `off` reverts the pre-ruling prompt byte-for-byte via env + restart, no redeploy).
- **THE HARVEST IS A SOURCE, NOT A GATE — the council must REASON to sibling terms (PO ruling 2026-08-09, verbatim: "this is just an example of how the Council and judge should be smart - 'this keyword came up (soccer), what might other people look for that is a similar keyword?' the answer in this case is football - so the keyword does not need to be pulled from JS, but the LLM can insert it in Description, Bullets or Keywords")**. Until now, essentially every term we place had to arrive as a Jungle Scout row, so a term the market obviously uses was unplaceable if the harvest happened not to return it. That is backwards: JS answers "how big is this term?", it does not define "what is this product called". **The council/judge must ask, of the design's OWN surviving on-theme terms, "what else would a shopper type for this?" and place the answer** — **SCOPE NARROWED BY THE PO 2026-08-09 ("B: NO, but backend yes"): BACKEND KEYWORDS ONLY.** A reasoned sibling is INVISIBLE INDEXING — it never appears in customer-facing copy. Bullets and description are explicitly OUT: on a US listing, "football" in shopper-facing prose for a soccer tee reads as an error rather than as international reach, and prose is where an off-target sibling does real brand damage. (The TITLE also stays out of scope here — it already has its own mechanism via `identitySynonymPhrases`, which mirrors pool phrases and inherits their real opportunity; that is the model to generalise, not duplicate.) This narrowing also deletes most of the adversarial risk found against the first design — prose keyword-stuffing, siblings contradicting garment facts in customer copy ("football jersey" on a graphic tee), and the editorial audit not running on section-regens all become moot once the target is backend bytes. GUARDRAILS (binding, from the rulings already in this file): (a) siblings must be grounded in THIS design's actual subject — the theme card / design name / surviving on-theme rows — never generic word association, because "Pixel Art Tee → art teacher" is exactly this mechanism failing; (b) a placed sibling carries **NO fabricated market data** — it must be distinguishable everywhere from a JS-measured keyword and must never display an invented volume or opportunity score (§5 "opportunity = the JS market metric, never our fabricated composite"); (c) it must not displace a market-attested CRITICAL keyword, only fill space the pool cannot; (d) it passes the same publish-boundary scrubs (trademark/celebrity) as any generated byte; (e) it must not contradict product FACTS — a graphic tee may index "soccer shirt" but must never be described as a jersey (§2 spec-truth beats coverage). Asymmetry from §3 still holds: soccer→football/futbol yes, football→soccer never.
- **Opportunity score = Jungle Scout's MARKET metric, never our fabricated composite** (PO 2026-08-08: "the Opp score should be a JUNGLE SCOUT opp score, NOT our fabricated one — it should not be changing from pull to pull and be used to make the right keyword placement decisions"). The displayed/decision-driving opp number must be the provider's market opportunity (stable across pulls unless the MARKET moves); the internal volume×usage-gap composite may exist only as a clearly-named internal gap signal, never labeled "opportunity" and never the placement decider.
- **Easy wins are never ignored (PO 2026-08-08: "we shouldn't ignore cases like cute christian shirts for women — 6.2 and super easy to rank")**: HIGH ease_of_ranking + decent market opportunity = a priority placement/target candidate even at modest volume — the winnable battles for a niche catalog. Ease must be a REAL decision input (as of the trace it influenced nothing); volume-first ordering must not bury ease-100 keywords.
- **RAW VOLUME IS NEVER THE DECIDER, AND NEVER A SILENT FALLBACK (PO 2026-08-09, verbatim: "VOLUME is not the biggest thing we look at but the JS opportunity and ranking ability with the right volume")**: proven live on B0GVV3XL4T — pool top row `usa soccer jersey` 1.98M/mo is unwinnable for a niche 2026 tee. Volume may only break ties BETWEEN rows that both carry market_opportunity. When a family has NO market data (0 rows scored, or research past TTL), the system must REFUSE to pick a money keyword on volume alone and must SAY SO to the seller — a confident-looking title built on volume-only ordering is a lie about the data behind it.
- **Targeting weighs ALL THREE factors explicitly (PO 2026-08-08: "We should look at all 3 Factors + Market opp + Ease + Volume to determine what to target")**: volume = size of the prize, ease = winnability, market_opportunity = the blend. No single-factor ordering; the target selector and placement decisions must consider the triple, with sanity floors so ease alone can't promote near-zero-volume junk.
- **Blank-brand placement waterfall (PO 2026-08-08: "if Comfort Colors is not in Title it needs to go to HIGHLIGHTS")**: the blank brand (Comfort Colors — only brands with brand_in_copy allowed; NEVER Gildan) must appear in the TITLE first; when the final title (incl. PO manual locks) lacks it, the Item Highlights MUST carry it as a deterministic fact. Enforce as a terminal net on the shipped IH bytes, not a prompt hint; runs on every title change including manual locks. IMPLEMENTED 2026-08-08: net = `ensureBlankBrandInHighlights` (src/lib/fba/blankSpecs.ts) — prepends `authentic <brand> blank` (prepend = survival through `capItemHighlightRepeats`' tail-drop at generation AND the push boundary), Gildan blocked by `brand_in_copy=false` data, ≥2-phrase compliance floor, idempotent. Wired into BOTH generator paths (buildItemHighlights LLM + fallback returns) with the PO's locked title threaded as `PipelineInput.lockedTitle`, and into the regenerate-item-highlight route (whose `recommended_title` IS the locked title). HARDENED 2026-08-08 (adversarial review): (a) the brand-INSERTION row is resolved from SPEC-TRUTH sources only — titles/productType/SKU style numbers, NEVER a search keyphrase — so a pool-contaminated "comfort colors" phrase can no longer stamp a false CC claim on a Gildan family (`resolveBlankRowForNet`, the ONE out-of-pipeline resolver); (b) the waterfall is satisfied only when EVERY shipped title (broadcast + per_child_titles) carries the brand; (c) the carry test is separator-blind ("Comfort-Colors" counts); (d) a title-only section regen re-nets the STORED IH against the new title, and the persist-time lock guard re-nets the fresh IH against the KEPT manual title (`applyBlankBrandNetToDetails` at both write-path sites); (e) every invocation emits a `BLANK_BRAND_NET` JSON decision line. DATA RULE: any new blank_specs row for a never-in-copy brand (every Gildan-family variant) MUST set brand_in_copy=false explicitly — NULL materializes as allowed. KNOWN GAP (out of GO'd scope): the lock-title route does not re-net the ALREADY-STORED IH at lock time — a lock that removes the brand from the title heals on the next IH regen/full regen, not instantly. STICKY-DETAILS PRECEDENCE (ruling 2026-08-08, adversarial review): the waterfall OUTRANKS the sticky-details standing approval — when a sticky-kept PO-ACCEPTED Item Highlight lacks the blank brand while the shipping titles also lack it, the net MAY rewrite the accepted string (this MUST is the newer standing rule, not LLM churn). The rewrite changes recommended_value only (current_value keeps the accepted/live value), so it surfaces as a fresh Push proposal requiring PO action — never ships silently — and the netted row is stamped value_source='spec' (blank_specs-derived) so the next regen's sticky gate reads it as a legitimate spec re-propose instead of re-running the snap→net cycle; every rewrite logs a `BLANK_BRAND_NET decision:'details-rewrite'` line.

## 8. BULLETS · DESCRIPTION · ITEM HIGHLIGHTS
- **Bullets**: exactly 5, each **150–200 chars**: `ALL-CAPS 2-3 WORD BENEFIT HOOK - one complete sentence.` Hook is a real benefit, never a label; never starts with a dash; garment brand named once (when it's a selling point); design name woven in; quality over coverage — clean 776 beats stuffed 900.
- **Description**: **900–980 visible chars**, HTML with `<b>` + `<ul><li>`, grounded in real facts (fabric/weight/dye/fit/neck/sleeve) + design story + styling; no search-phrase prose, no brand in body, no internal jargon (seller/SKU/ASIN/listing/keyword/backend).
- **Item Highlights** (title_differentiation): **≤125 chars, aim 110–125** (PO ruling 2026-08-10, raised from ≤75), 3–5 short benefit PHRASES (no sentences), customer-facing (never a keyword list), adds what the title lacks, no word repeated >2×, no promo language. Written as COPY, never a bare fact-join (PO 2026-08-04: "Cotton tee, Crew Neck, for women" class rejected) — each fact pairs with a feel/benefit word; no title-echo.
  - **WHY 125 (PO ruling 2026-08-10, reversing PO 2026-07-19)**: Amazon's own title-update FAQ states the 200 indexable characters are **split between "Item name (75 characters) and Item highlights (125 characters)"**, and that *"Item name and Item highlights are both inputs for search, and one isn't prioritized over the other."* Capping at 75 therefore threw away **50 of 125 characters (40%) of an INDEXED, shopper-visible field on every listing in the catalog**. Verified at the primary source, not from vendor commentary.
  - **WHY IT WAS 75, and why that reasoning expired**: the budget was **already 125** and was cut to 75 on 2026-07-19 because the 125-char version shipped a rambling ~120-char comma-sentence live (B0FKKN8XKV). *The rambling was the defect; the budget was not.* The other half of the rationale — "Amazon's field shows next to a ≤75-char title" — expired 2026-08-10, when Amazon moved Item Highlights to display **beneath** the item name on desktop and mobile. So the cure keeps what actually worked (short comma-separated phrases, NO sentence punctuation, copy tone) and restores the space.
  - **ONE constant, not six**: the budget now lives at `CONTENT_CONTRACT.itemHighlights.max` (125) / `.fillTarget` (110) and is referenced by the generator gate, the validator, the terminal net (`productDetailAttrs`), the LLM brief, and the tests — it was previously a literal `75` in each, which is how it drifts.
  - **DO NOT CONFUSE with the item_name ≤75 DEPENDENCY**: Amazon error **100476** is *"Provide an Item Name that is 75 characters or less to use Item Highlights"* — a rule about the **TITLE**, unchanged. Every 75 in the title path and in the 100476 heal stays 75.
- **UNISEX FIT CLARITY (PO 2026-08-06)**: the whole current catalog is UNISEX blanks marketed to WOMEN. The listings MUST make the unisex sizing explicit — but ONLY in Bullets, Description, and Features/Item Highlights. **NEVER in the Title** ("it should not be stuffed to TITLE"). Department stays Womens / target_gender female (the targeting is the strategy; the copy sets the fit expectation). Standard phrasing: "Unisex sizing runs relaxed — many women size down one for a fitted look." Driven by `blank_specs.unisex` (DB flag; migration 054) → deterministic guarantees in `applyTerminalNets` (bullets clause + description note) + IH fact. Fit-to-Size sentiment stays spec-truth (unchanged by this rule). **The "NEVER in the Title" half is now ENFORCED (2026-08-09), not just asked for**: `stripTitleWasteVocabulary` removes "Unisex" (and "Classic Fit", §3 gold rule 4) from the shipped title bytes at the `bandTitle` seam, under the PO's guard — only when the removal frees space for a money keyword or the title still lands 70-75. TITLE-only: these three fields keep the facts.
- **Product Detail attributes**: values ground to the spec table where a fact exists (Fit, Sleeve, Stretch binary+graded, Fit-to-Size, Collar: Crew Neck → "Round Collar" — the enum has no Crew member). **Model Name carries NO brand** (PO 2026-08-04): the Brand attribute already says it; "THE CEO Cupid Valentine" → "Cupid Valentine" (deterministic strip of seller + garment brand).

## 10. SHIPPING & OPERATIONS
- **Nothing writes to live Amazon without explicit PO GO** — the PO personally clicks Ship. An approved plan is standing authorization for its phases; ship actions are the reserved stop.
- Pushes go to **BOTH FBA and FBM twin SKUs** per ASIN (+ parent SKU for titles); push is **UPDATE-ONLY** (never PATCH an offerless SKU — phantom-listing risk); all pushes route through the serial durable queue with the global 5-req/s bucket.
- **Verification is automatic** (PO verbatim 2026-06-13): cron verifies every push against live Amazon, re-ships until 100%, notifies only on major flags.
- **Initial Ship = standing approval for that field** (PO 2026-08-08: "it was always required that the system completes this in a loop automatically so user does not see anything incomplete after initial push"): once the PO has shipped a core field for a family, later regen updates to that field's recommendation auto-flow to Amazon (content-reconcile loop) — the PO's review gate applies to the FIRST push of a field, and to fields never shipped before. Delivery-retry (same content) and content-reconcile (updated content, previously-approved field) are distinct loops; both are bounded, loud-logged, and kill-switchable.
- A shipped section **locks for 7 days** ("settling") so scores can't nag; per-section override exists.
- Behavior changes ship **off → shadow → on** with live-regen evidence gates; scorer re-bases are announced, and the PO accepts truth-fix score movement (the 72→70 dip is a rubric fix signal, not a content problem).
- Jungle Scout budget: **950 billable calls/month** self-cap (50 under plan).

## 11. QUALITY PRINCIPLES (anti-Goodhart)
- Terminal nets pad **only from product facts** — never pool terms, never invented adjectives. A number made green with junk is a failure.
- The scorer never reads the ship door's violations; a rising "repaired" count is a producer regression signal.
- Preserve-prior fires only when the fresh output is empty/unparseable OR strictly worse — and a contaminated prior is never "better".
- Honest claims: the optimizer controls **indexing/relevance only** — "indexed for", never "will rank #1".
- The PO's qualitative gate: padded copy must read like a product, not filler — the PO reads samples and the read outranks the numbers.
